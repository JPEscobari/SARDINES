# Phase 2A / 2B: persistent Promise storage and review

## Implemented boundary

Analysis remains `POST /api/ingest`, with `persisted: false`. An explicit Save for Review submits `{sourceType, content, analysis}` to `POST /api/review/sources`. The server validates the strict extraction schema and every source quote again before writing. Client-supplied identities, record IDs and approval fields are rejected. This checks structure/evidence, not model origin or semantic truth: saved analysis is labelled submitted_for_review, not authenticated AI output.

The dashboard adds Save for Review and a stored Promise Queue. Reviewers can edit title, customer, owner, relative date wording, a resolved UTC deadline and operational status. These edits are unauthenticated local development edits, not approvals. The original Chat, Task, Decision and ingestion panels remain. Mongo-dependent routes return 503 promptly when disconnected; their models and persistence are unchanged.

## Storage choice and runtime

The local adapter uses Node's built-in `node:sqlite`, tested with Node 24.14.1 (SQLite 3.51.2). Use Node 24 for this development batch; this runtime currently emits an experimental SQLite warning. No new npm dependency was added.

Default absolute database path: `E:/Project_git/SARDINES-integration/server/data/operational.sqlite`. `SARDINES_DB_PATH` can override it without editing .env. SQLite may maintain adjacent `-wal` and `-shm` files. The default data directory is Git-ignored. If overriding the path, keep it outside source control and protect its permissions.

Stored entities: immutable source text and original analysis (including blockers/summary), reviewed Promise records, proposed Action records, and AuditEvents. Source text is stored in plaintext locally; it is not written to application logs. This is a single-machine development datastore, not cloud persistence. Do not use a network-mounted filesystem. Synchronous queries block the Node event loop; list endpoints are currently unpaginated. Back up using SQLite's supported backup mechanism or after all database connections close; copying just the main file while WAL writes are active is unsafe.

WAL, synchronous=FULL, a 5-second busy timeout and BEGIN IMMEDIATE transactions protect writes. A source, its promises/actions and audit entries commit together or roll back together. Duplicate source identities return existing records, preserving review edits. The identity is SHA-256 of sourceType + NUL + exact content. Whitespace changes and different source types are distinct submissions. A duplicate does not replace the original analysis or produce extra audit events. Differently sourced but text-identical events of the same type are intentionally deduplicated in this local MVP; richer external source identities are future work.

## OperationalRepository contract

Public operations return Promises. Domain validation is in `server/operational/validation.js`; `LocalRepository` implements the following interface. A Cloudant adapter must satisfy the same tests and invariants before selection.

| Method | Input | Result |
| --- | --- | --- |
| saveAnalysis | {sourceType, content, analysis} | {source, promises, actions, duplicate} |
| getSource | source ID | Source or null |
| listPromises | none | Promise[] |
| getPromise | promise ID | Promise or null |
| updatePromise | ID, {version, ...reviewFields} | updated Promise |
| listActions | optional source ID | Action[] |
| proposeAction | source ID, extraction action | unapproved Action, idempotent by description/evidence per source |
| listAuditEvents | none | AuditEvent[] |

All IDs are generated by the backend. Source IDs are deterministic hashes; other IDs are typed UUIDs. Records carry version and creation/update timestamps. Validators reject additional properties. Reviews require the version read by the client; stale writes return 409. Status transitions: needs_review -> open/blocked; open -> needs_review/blocked/completed; blocked -> needs_review/open/completed; completed -> open. Staying in the same state is allowed. State changes never approve external actions.

Extraction dueAt is retained as extractedDueAt but never promoted automatically. Stored dueAt starts null with deadlineState=unresolved. An explicit review may supply a canonical, calendar-valid UTC ISO timestamp such as 2026-11-22T17:00:00.000Z. It is marked reviewed, not authorized for scheduling. Changing date wording clears an old resolved deadline unless explicitly supplied again. Missing owner/customer/deadline remain null. No directory IDs are inferred.

Actions belong to a source and initially have promiseId=null. The current extraction schema has no reliable action-to-promise relationship, so the UI labels them same-source suggestions with unresolved linkage. Approval is pending and execution disabled. No outbound adapter exists. Audit events record entity ID, event type, time and changed field names, with actorId=null and actorType=unauthenticated_local. They do not establish a human identity or retain full before/after revision history.

## HTTP contract

Success envelopes use success=true; errors use `{success:false,code,error}`. Invalid input -> 400, wrong content type -> 415, unknown record -> 404, stale version -> 409, storage failure -> sanitized 503.

- POST /api/review/sources: 201 on first save, 200 on duplicate; persisted=true.
- GET /api/review/sources/:id: original evidence and analysis.
- GET /api/review/promises and GET /api/review/promises/:id.
- PATCH /api/review/promises/:id: allowlisted review fields plus required version.
- GET /api/review/actions?sourceId=...: pending suggestions only.
- GET /api/review/audit-events: local audit entries.

There is deliberately no approval, action execution, or public action-proposal endpoint. The repository proposeAction operation is available for a future validated workflow. With NODE_ENV=production the review router fails closed with 503. The backend now binds to 127.0.0.1. This is not authentication: any local process/user can access records or make review edits. Production requires authenticated, authorized, tenant-scoped access, CSRF/origin controls as applicable, retention rules, encryption, rate limits and pagination before exposure.

Future approval design: an authenticated server principal submits action ID + expected revision. Server authorization verifies account/tenant access and approval rights, then atomically records approved payload hash, actor subject, timestamp and revision. The execution worker accepts only that approved immutable payload. Edits invalidate approval. Client usernames are never accepted as identity. External retries require idempotency and reconciliation of unknown outcomes. None of that is enabled in this batch.
